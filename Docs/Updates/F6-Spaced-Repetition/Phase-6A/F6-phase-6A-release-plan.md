## Recovery distinctions and monitoring contract

**Disable reviews** is an availability control, not schema rollback: receipts remain durable; ordinary replay/resume is gated while disabled and can recover after safe re-enable. Keep enrollment coordinated unless its writer behavior itself is the incident. **Binary rollback** should retain additive schema and requires proven old-binary compatibility, preserved flags/config and an approved artifact path consistent with release safeguards. Old writers may create gaps/stale states; reactivation needs catch-up and reconciliation. **Database forward recovery** retains schema/data while correcting an inspected failure. **Database restore** can lose all writes since backup, including unrelated personal/quiz data, and must meet approved RPO/RTO. **Down** deletes learning/session/receipt/history data and the mapped column; it is test-only here and requires exceptional separate authorization for production.

Before activation, assign collection method, numeric threshold, evaluation window, pager/escalation route and response for API 500/503 rates and latency; disabled vs database-failure 503s; retries/deadlocks/timeouts; stale/submission conflicts; pending/expired sessions and receipt recovery; missing/stale enrollment and blocked ratios; table/key/disk growth; restarts/key errors; authentication/owner failures; and legacy quiz/vocabulary health. Existing application logging is not evidence of deployed dashboards or all these metrics. Accepted sessions/history follow approved P4 saved/account lifetime; storage forecasting and operational evidence retention remain decisions, not permission to prune receipts.
