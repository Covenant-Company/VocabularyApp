## 3. ASP.NET Core Findings

Program.cs:117-136 executes Swagger/UI, default files/static files, CORS, authentication, authorization, controllers, and anonymous SPA fallback in that order. UseHttpsRedirection remains commented at line 124. No UseHsts, AddHsts, UseForwardedHeaders, ForwardedHeadersOptions, RequireHttps, HTTPS port selection, or custom insecure-scheme rejection was found.

Authentication precedes authorization correctly. Public static content and minimal-host routing are not defects. Swagger can short-circuit before the commented redirection location; simply uncommenting that call would not provide complete application-level coverage.

**R1 is now a Confirmed defect:** the production login SPA is served over HTTP without upgrading. This is no longer conditional on unknown host enforcement. Source behavior explains the exposure, while the user’s observation proves the actual insecure entry point. Individual HTTP API operations were not exercised.

**R2 remains a Potential risk, Medium:** no Strict-Transport-Security header was observed on the tested HTTPS /login 304 response. That is a confirmed observation, not proof of absence on all responses, cached responses, or all browser policy state. In this credential-bearing browser app, HSTS is useful protection against later insecure navigation, especially once redirection exists; it is not a substitute for fixing R1.

HSTS ownership comparison:

| Candidate | Assessment |
|---|---|
| ASP.NET Core managed | Recommended: source-controlled, environment/domain scoped, naturally conditioned on HTTPS, and covers app-generated HTML/static/API responses when placed before short-circuiting middleware |
| IIS/root web.config managed | Viable if conditional header handling is reviewed; an unconditional custom header is not a substitute for an HTTPS-aware policy. Adds IIS-specific response handling that is unnecessary for the current app scope |
| Host/native IIS managed | Viable with verified access, persistence and a single owner, but no such enabled control is established. IIS/10.0 alone does not establish the precise build or availability of native HSTS |
| Deferred | Defer activation until HTTPS enforcement and certificate operations are validated, but retain HSTS within PSH-1 scope |

Native IIS HSTS is site-level configuration and supported in IIS 10 version 1709 onward; it is not an arbitrary application web.config element. [Microsoft IIS HSTS configuration](https://learn.microsoft.com/en-us/iis/configuration/system.applicationhost/sites/site/hsts).

Recommendation: application-managed production HSTS scoped to the supported production host, placed before Swagger/static files/authentication endpoints. Begin with a short, explicitly reviewed duration after enforcement validation; increase only with operational confidence. Do not enable preload or includeSubDomains: subdomain coverage and ownership requirements have not been established. Ensure temporary/shared hostnames do not unintentionally acquire this policy.

A long cached HSTS policy can make certificate expiry or HTTPS failure a persistent outage for returning clients. Removing a server setting alone does not clear clients' stored policy; recovery requires functioning HTTPS and appropriate policy expiration/reset. Certificate renewal and HTTPS-preserving recovery therefore belong in acceptance constraints. HSTS does not secure an arbitrary client's first HTTP request. [Microsoft HTTPS/HSTS guidance](https://learn.microsoft.com/en-us/aspnet/core/security/enforcing-ssl?view=aspnetcore-8.0).

## 4. IIS / web.config Findings

The root artifact is an ASP.NET Core ANCM configuration, not the Angular-only rewrite file. VocabularyApp.UI/public/web.config rewrites non-file/non-directory routes excluding /api to index.html and registers WebP MIME type; it contains no HTTPS rule. The workflow excludes it, and publish/deploy checks reject nested web.config files. Keep those safeguards.

The supplied provider documentation describes a 1-Click force option and a manual root web.config rule checking whether HTTPS is off, then performing a permanent redirect. This establishes the provider-supported rule concept, **not where the current 1-Click implementation persists its setting**. No exact provider documentation URL or generated control-panel configuration was supplied, so the storage conclusion must remain unknown.

Authoritative enforcement comparison:

| Option | Fit and advantages | Limitations | Recommendation |
|---|---|---|---|
| A — 1-Click Force HTTPS | Provider-supported; HTTPS prerequisite is now satisfied; can enforce before the application | Inactive; persistence surface unknown; not reproducible from this artifact if it edits only deployed content | Do not use as the long-term sole authority without persistence evidence |
| B — source-controlled root IIS rewrite | Runs before managed Swagger/static/API processing; provider documents IIS rewriting; artifact supplies the policy every deployment | Requires correct integration with generated ANCM XML, delegated rewrite support, scheme condition and domain/path testing | **Preferred single redirect authority** |
| C — UseHttpsRedirection | Source-controlled, compatible with direct in-process IIS when configured correctly | Requires correct early ordering, HTTPS target/port and scheme; cannot cover responses handled outside the managed app | Valid alternative, not needed in addition to B |
| D — combination | IIS redirection plus application HSTS serves distinct purposes | Multiple HTTP redirect owners add configuration ambiguity and loop risk without demonstrated need | Use B plus separately owned HSTS, not A+B+C redirect duplication |

Option B means a reviewed source WebApi configuration or publish transform contributing the rule to the **root artifact**, not a handwritten edit on the destination or repurposing the Angular file. Web SDK publishing can generate or transform ANCM configuration; preserve processPath, arguments and in-process hosting validation. [Microsoft Web SDK configuration documentation](https://github.com/dotnet/AspNetCore.Docs/blob/main/aspnetcore/host-and-deploy/iis/web-config.md).

Planning constraints: target the known canonical HTTPS authority; do not reflect arbitrary Host values or assume the temporary hostname has this certificate. Preserve paths, query strings and escaping. Verify HTTPS requests do not re-enter the redirect. Distinguish browser GET/HEAD navigation from unsafe API methods; do not blindly apply a permanent POST redirect that changes semantics. No secret-bearing HTTP request can be made safe retroactively. Renewal challenge behavior and approved aliases require explicit accommodation if applicable. No XML rule or implementation sequence is prescribed here.

**Will CI/CD overwrite Force HTTPS?** Precisely:

| Persistence surface | Current contentPath sync behavior |
|---|---|
| Destination-only file absent from artifact | DoNotDeleteRule prevents deletion; preservation of that file does not establish enforcement precedence |
| Root web.config present in both artifact and destination | Sync can replace destination contents with the artifact; no merge, HTTPS-specific skip, or rule-preservation mechanism exists |
| Parent/server IIS configuration outside the deployed directory | Not directly synchronized by this contentPath operation; inheritance/locks and provider behavior still matter |

Thus **if 1-Click writes the deployed root file, a later deployment can remove its rule**. If it writes external IIS configuration, this content sync does not directly overwrite that surface. Neither repository code nor the supplied panel description proves which case applies. R3 stays a conditional Potential risk; no rule was activated or observed being lost. Selecting B avoids reliance on the unknown persistence of the inactive control.

## 5. Reverse Proxy / Forwarded Headers Findings

Searches still show no explicit forwarding middleware/options, X-Forwarded-Proto processing or known-proxy configuration. The observed HTTPS port 443, IIS responses and in-process publish checks support direct IIS handling; there is no affirmative evidence of an additional TLS-offload proxy requiring forwarding.

**R4 is reclassified Externally verifiable, not a current remediation requirement.** Exact internal topology and Request.Scheme were not directly observed, but their remaining uncertainty does not justify speculative middleware. For in-process IIS TLS termination, the server derives scheme from native SSL status. [ASP.NET Core IIS implementation](https://raw.githubusercontent.com/dotnet/aspnetcore/v8.0.0/src/Servers/IIS/IIS/src/Core/IISHttpContext.cs).

Out-of-process IIS integration has separate automatic forwarding behavior; this artifact expressly validates in-process hosting. [Microsoft proxy integration guidance](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-8.0).

Recommendation: no UseForwardedHeaders in the PSH-1 baseline. Acceptance checks must establish no HTTPS redirect loop and correct HSTS emission. If that fails because a real proxy boundary is discovered, inspect trusted peers, header replacement and hop count before changing forwarding. Never trust arbitrary client X-Forwarded-Proto or clear trust lists as a workaround. Runtime patch matters if forwarding becomes necessary because ASP.NET Core 8.0.17 tightened unknown-proxy handling. [Microsoft servicing change](https://learn.microsoft.com/en-us/dotnet/core/compatibility/aspnet-core/8.0/forwarded-headers-unknown-proxies).

Incorrect scheme could affect redirects, generated absolute URLs and application HSTS. Current JWT validation is not scheme-dependent; no external OAuth redirect flow, request-derived absolute URL generation or client-IP-based authorization was found. Security-log address interpretation is a separate conditional concern, not an observed failure.

## 8. CORS Findings

**D1 — Confirmed defect, Medium, remains a PSH-1 remediation item in repository production defaults.** appsettings.json:15-20 allows the HTTP temporary-site origin and both localhost:4200 schemes; Program.cs:16-21 falls back to localhost. Development settings repeat development origins, but publishing removes that file and retains base defaults. No environment-specific production separation exists in Program.cs.

The verified production UI/API share https://myvocabularybuilder.org, so **production CORS grants are not needed for this architecture**. No Access-Control-Allow-Origin header on the observed same-origin response is normal and does not establish either a broken policy or the effective cross-origin allowlist.

Recommendation: no production cross-origin permission by default; keep localhost permission explicitly in Development. Do not add the canonical production origin to CORS merely because HTTPS was enabled. Any future cross-origin client needs a separately justified HTTPS allowlist. Ensure absence of a production list does not trigger the current localhost fallback, and account for configuration-array merging and external overrides.

WithOrigins is explicit; no wildcard origins or AllowCredentials were found. AllowAnyHeader/AllowAnyMethod does not grant unauthenticated access; HTTP-origin permission does not expose HTTPS localStorage. The risk is unnecessary trust in insecure/development browser origins, conditional on token/credential availability and the effective policy, not a proven exploit. AllowedHosts="*" is separate host filtering.

The publish script pins a SHA-256 digest of reviewed base settings. Future remediation must review/update the digest along with intended defaults rather than bypassing the check. No configuration was edited here.

## 9. CI/CD and Deployment Findings

The single workflow builds/tests, stages Angular into wwwroot, validates a portable publish artifact and deploys it in deploy-production. Publish validates ANCM and excludes nested configuration, development settings and certificate/key/profile files. Deploy uses contentPath with DoNotDeleteRule and AppOffline; certificate/app-pool/content extension links are disabled. HTTPS MSDeploy is required with no allowUntrusted or custom certificate bypass.

These remain **Correctly configured** safeguards. They neither install the public certificate nor preserve arbitrary destination edits inside root web.config. R3’s file/configuration distinction is explained in section 4.

**R5 — Potential risk, Medium:** there is no automated public HTTPS acceptance step. The new manual evidence verifies real HTTPS functionality but does not provide recurring protection against a future redirect/header regression.

Recommend automated **post-deployment acceptance** within deploy-production, immediately after successful MSDeploy and application recovery from AppOffline, under the same production concurrency lock. Failure should fail the deployment job’s acceptance outcome, not be ignored. These are not pre-deployment gates that can prevent an already completed content change, nor proof that a failed check rolled deployment back. Artifact configuration checks can separately gate upload/deployment.

Do not silently make lookup public, place tokens in URLs/logs, or assume existing CI production credentials. This bounded choice is a planning decision, not a blocker.

Use no certificate bypass, no credentials on HTTP, no state-changing add-to-vocabulary automation, and bounded readiness polling. Fresh requests avoid confusing a cached page with current behavior. Verify policy persists after a subsequent normal deployment. Existing manual functional checks remain complementary.

## 14. Recommended Remediation Scope

PSH-1 should encompass source-controlled IIS enforcement, validation of its persistence under content synchronization, production CORS separation, accurate HTTPS documentation, cautious application HSTS after enforcement validation, and CI/CD post-deployment transport acceptance.

Keep one HTTP redirect owner. Keep SmarterASP.NET certificate ownership and the portable in-process publishing model. Do not rely on a destination-only edit, activate redundant 1-Click redirection, or add UseHttpsRedirection alongside the IIS policy without new justification.

Remaining operational uncertainties are handled by planning constraints: inspect effective configuration before deployment, validate path/query and scheme behavior, account for renewal, retain a known-good configuration/artifact, and recover without deliberately returning users to insecure login. HSTS recovery must retain working HTTPS because browser policy can outlive server rollback. These are requirements for the future plan, not an implementation plan or authorization to deploy.

No forwarded-header changes, certificate packaging, authentication redesign, or general security expansion is recommended.
